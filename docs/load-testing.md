# Нагрузка очереди проверок — HPRPR-14

## Воспроизведение

```sh
make test-load
# Другие параметры:
LOAD_N=100 LOAD_CONCURRENCY=8 LOAD_MATRIX='1:1 1:2 2:1 2:2 4:1' make test-load
# Для обычных соседних клонов дополнительно INFRA_DIR=../infra.
```

Используются те же Compose-стенд, Keycloak, REST grpc-gateway, PostgreSQL,
SeaweedFS и настоящий Docker, что и в `make test-integration`. Программа
`test/load/main.go` создаёт уникального студента, SQL-фикстурой выдаёт ему Pro,
через автора загружает и публикует задание с двумя тестами (открытый и закрытый).
Решение на Python 3.14 складывает два числа. Один прогрев выполняется до замера;
скачивание образа и настройка задания в цифры не входят. Остальные программы
и тестовые workload во время измерений не запускаются.

N=40 измеряемых посылок в каждом опыте, одновременно до 8 запросов/ожиданий.
Каждая горутина отправляет REST-посылку и держит NDJSON watch до DONE, затем
берёт следующую. Время — от начала POST до полученного DONE, включая очередь,
S3, создание/уборку песочницы и два Docker-запуска. Это ограниченная конкуренция
клиента, не генератор с фиксированной частотой поступления и не тест переполнения.
FAILED/SE, другой вердикт, HTTP/streaming/transport error, timeout и преждевременный
EOF учитываются как ошибки, ненулевое число ошибок завершает программу с кодом 1.

Пропускная способность = успешные посылки / полное время измерения × 60.
Перцентили успешных посылок — nearest-rank от отсортированных измерений:
ceil(N×p), без интерполяции. p99 при N=40 фактически максимум, выборка небольшая.
Сырые отсортированные времена, параметры, число ошибок и длительность сохраняются
в `test/load/results/<replicas>x<WORKER_CONCURRENCY>.json`. Параметры масштабирования
применяет Compose, драйвер получает те же значения в метаданных результата.

## Выводы и границы

- Два слота вместо одного дали примерно 1,71× throughput и снизили p95 с 3,49
  до 2,04–2,08 с. Один процесс с двумя слотами и два процесса по одному дали
  близкие результаты: 236,97 и 235,43 посылок/мин.
- Четыре слота дали примерно 2,50–2,51× к одному: 345,72–347,08 посылок/мин.
  p95 снизилась до 1,42–1,45 с. Увеличение числа слотов не даёт линейного роста:
  здесь существенны создание контейнеров и общие ресурсы Docker Desktop.
  Последнее — объяснение по характеру workload, отдельный профиль CPU/I/O не снимался.
- У четырёх реплик по одному слоту нет заметного выигрыша перед двумя по два:
  разница throughput около 0,4% в одном опыте. Этих данных недостаточно, чтобы
  объявлять одну схему масштабирования быстрее или оценивать статистическую значимость.
- Реально обработаны все 200 посылок, у каждой получены DONE и OK через watch;
  HTTP/streaming/system errors — 0. Сырые времена позволяют пересчитать перцентили.
- Это короткий тест очереди на простом Python с двумя тестами, без компиляции.
  Он не измеряет длительную устойчивую нагрузку, тяжёлые Go/Java-компиляции,
  десятки тестов в задании, mixed workload, истечение аренды/падение worker,
  предельную ёмкость очереди или поведение при исчерпании памяти машины.
  Для sizing нужны более длинные серии с реальными заданиями и повторами.

После прогона выполнен `down -v --remove-orphans`: контейнеры, сеть и named volumes
нагрузочного стенда удалены. Базовые образы и локальные результаты сохранены
для воспроизведения; постоянные env и конфигурация Docker не менялись.
