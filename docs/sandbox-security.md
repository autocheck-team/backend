# Проверка безопасности песочницы — HPRPR-24

Проверено 18 ноября 2026 на настоящем Docker Engine 29.6.2, Linux/arm64 в Docker Desktop,
cgroup v2, runtime runc 1.3.6; Go 1.27.4. Образы: `python:3.14-alpine`, `gcc:15`.
Полный набор тестов также проверяет компиляцию и вердикты Go, C++, Python и Java.

## Воспроизведение

```sh
make test-sandbox-security
```

Цель сначала проверяет доступность Engine, затем запускает тесты с `-race -count=1 -v`.
При обычном `go test` отсутствие Docker означает skip, как в существующем
`internal/judge/docker_test.go`. Ошибки скачивания образов и выполнения тестов не скрываются.
Нужен Linux Docker с работающими memory/pids cgroup и seccomp. Отдельные Postgres,
S3, Keycloak и API для матрицы не требуются.

`internal/judge/security_docker_test.go` передаёт исходник пользовательского решения
в настоящий `judge.Runner → Docker → sandbox.Workspace.Run`; C++ сначала компилируется.
Репозиторий заданий и объектное хранилище заменены существующими тестовыми стабами.
Команды, лимиты, передача stdin, обработка stdout/stderr, выбор вердикта и запуск
custom-чекера проходят рабочий код. Изоляционные пробы дают OK только после проверок
недоступности ресурсов; неожиданный успешный доступ ломает тест.

Все атаки выполняются последовательно. До fork/thread/memory-нагрузок решение проверяет
значение соответствующего cgroup-лимита. Перед заполнением workspace проверяется его
размер. После каждого сценария проверяется, что отдельный контрольный контейнер жив.
Он запускается с собственными лимитами и удаляется тестом.

## Найденные проблемы и исправления

1. **Не было общей квоты workspace.** `RLIMIT_FSIZE` ограничивал только один файл,
   а обычный volume позволял создавать следующие. Регрессия с конечной нагрузкой:
   старый volume принял **335544320 байт (320 МиБ)**; новый — **268431360 байт**,
   затем `ENOSPC` (часть 256 МиБ занял исходник). Теперь используется local tmpfs volume
   с лимитом 256 МиБ и 16384 inode, `mode=0755,nosuid,nodev`.
   Один контейнер keeper удерживает mount между компиляцией и тестами: без него Docker
   размонтировал бы tmpfs после каждого запуска и потерял бинарники. Keeper также
   работает без сети/capabilities, с read-only rootfs, лимитами 16 МиБ и 4 процесса.
   Close удаляет keeper перед volume; Sweep учитывает для него срок workspace 2 часа.
   Это дополнительный расход RAM и один служебный контейнер на активный workspace;
   квота не резервирует всю память заранее, но файлы tmpfs расходуют память хоста.

2. **Штатный seccomp разрешал ptrace между процессами того же UID.** До исправления
   C++ вывел `PTRACE_ALLOWED`, остановил PID 1 через PTRACE_ATTACH и дошёл до TL
   примерно через 3.3 с. После исправления ptrace возвращает EPERM, проба даёт OK.
   Встроен [профиль Moby](https://github.com/moby/profiles/blob/f862455628f78f84c937e967e4a03902fb1dee11/seccomp/default.json),
   commit `f862455628f78f84c937e967e4a03902fb1dee11`: из всех разрешающих правил удалены
   `ptrace`, `process_vm_readv`, `process_vm_writev`, пустое правило удалено.
   Остальные правила и defaultAction=ERRNO сохранены; blacklist вместо Docker allowlist
   не используется. Копия лицензии Apache-2.0 — `internal/sandbox/seccomp.LICENSE`.
   При обновлении Docker профиль нужно пересматривать вместе с тестами всех языков.

3. **Окружение PID 1 читалось процессом того же UID.** В контролируемом сравнении
   прежних настроек прочитано 211 байт `/proc/1/environ` (значения не выводились).
   Файл теперь маскируется; проверка требует отказ либо пустое содержимое. Это
   окружение контейнера, доказательств чтения окружения хоста не обнаружено.
   Явный MaskedPaths сохраняет стандартные proc-маски; CPU sysfs закрыт целиком,
   включая thermal_throttle, без зависимости от количества CPU хоста.

4. **Ошибки уборки скрывались.** Ошибка удаления контейнера теперь возвращается
   песочницей; Runner возвращает ошибку Close workspace решения и чекера, сохраняя
   исходную ошибку через errors.Join. Это отдельно проверяется unit-тестом.
   Дополнительно отключён Docker log driver: вывод уже хранится в ограниченном
   буфере воркера и не требует второй копии в файлах daemon.

## Память воркера и границы измерения

Во время трёх бесконечных потоков каждый запуск завершился после 16 МиБ суммарного
вывода. Измерения процесса теста с `-race`: heap перед/после stdout — 2.7/71.9 МБ,
stderr — 72.0/52.5 МБ, смешанного потока — 52.6/57.3 МБ; TotalAlloc за запуск —
примерно 158/102/170 МБ. Это включает Runner и тестовое S3-хранилище, которое
дополнительно копирует sample stdout в память. Тест ограничивает TotalAlloc
256 МиБ на сценарий и проверяет ровно 16 МиБ сохранённых данных. Это ограниченный
прогон, а не доказательство отсутствия утечек при длительной эксплуатации.
Docker stats даёт приблизительные значения и может пропустить короткий пик OOM.

## За пределами проверки

- runsc/gVisor отсутствует среди настроенных runtimes Docker: проверен runc,
  изоляция ядра через gVisor не проверена. Локально проверена только arm64.
- Не проверялись неизвестные уязвимости ядра, runc, Docker, компиляторов и образы
  с вредоносной доверенной обвязкой; Docker socket самого воркера остаётся доверенным.
- Матрица запускает production Runner, но не REST/gRPC, Keycloak, очередь и настоящий S3.
  Их интеграция не менялась. Проверка соседнего контейнера — контроль живости,
  не нагрузочный SLA/latency-бенчмарк всего хоста.
- Чтение публичных файлов runtime (например, `/etc/passwd`, `/proc/self/status`) допустимо;
  полной недоступности `/proc` и `/sys` не заявляется. `/tmp` и `/dev/shm` — отдельные
  ограниченные writable tmpfs; корневая ФС остаётся read-only.
- Контейнеры решения и namespace проверяются через Engine API, без прямого аудита
  всех процессов Linux VM с привилегиями хоста. Сценарии не являются pentest ядра.
- Проверка рестарта daemon, падения хоста и исчерпания ресурсов сразу многими
  воркерами не проводилась; квоты действуют на workspace/контейнер, не на весь кластер.

API, proto и схема БД не менялись; миграции не добавлялись.
